# Security model

## Trust zones

| Zone | Components | Trust level |
|---|---|---|
| Client RAM | keys, plaintext, decrypted drops | trusted during session only |
| Server | Go backend, SQLite, Tor hidden service | semi-trusted; stores ciphertext only |
| Tor network | relays/onion transport | untrusted for content confidentiality |
| External environment | ISP, firmware, hardware, observer | untrusted/out-of-scope depending on attack |

## In-scope protections

- post-session client artifact reduction through tmpfs and panic wipe;
- Tor-only client egress enforcement;
- DNS redirection to Tor DNSPort;
- IPv6 disablement and ip6tables DROP;
- server-side ciphertext-only storage;
- no IP/hint/payload request logging;
- authenticated encryption tamper detection;
- TTL-based retention limits;
- no identity/accounts.

## Out-of-scope threats

- global Tor correlation;
- compromised firmware/BIOS/UEFI;
- cold-boot RAM extraction;
- hardware keyloggers or cameras;
- malicious ISO supply chain if users skip hash verification;
- compromised recipient private key;
- coercion.

## Security invariants

| ID | Invariant | Implementation |
|---|---|---|
| I-01 | firewall failure blocks networking | `deaddrop-firewall.service` before `network-pre.target` |
| I-02 | client starts only after Tor bootstrap | `ExecStartPre=/usr/local/bin/wait-for-tor` |
| I-03 | panic daemon starts early | `After=basic.target` |
| I-04 | AES-GCM nonce generated by CSPRNG | `crypto/rand` |
| I-05 | decryption errors are opaque | generic `decryption failed` |
| I-06 | no plaintext DB fields | schema has `id,hint,payload,created_at,expires_at` |
| I-07 | server has no content keys | no server encryption keys except Tor onion key |

## Residual risks

### Shared onion rate limiting

The backend sees Tor hidden-service traffic as loopback. DEADDROP-OS strips ephemeral ports to avoid a memory leak and bypass. To reduce shared-bucket starvation, the server issues a proof-of-work challenge when a bucket is exhausted. Future work may add Tor-circuit-aware accounting if safely exposed.

### QEMU environment dependence

The repository includes a QEMU packet-capture harness and guest E2E hooks, but complete active onion lifecycle validation requires a lab topology with a test onion server and capture interface.

### Panic wipe limitations

The daemon best-effort overwrites/removes configured paths. It does not defeat cold-boot attacks or malicious kernel/filesystem behavior. The client architecture assumes tmpfs paths so shutdown/power loss clears session data.
