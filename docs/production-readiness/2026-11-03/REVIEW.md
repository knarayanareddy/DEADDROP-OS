# DEADDROP-OS review

## Scope and verdict

Pinned revision: `38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9`. This implementation is described as a release candidate. The [README:3–5](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/README.md#L3-L5) claims local release checks passed while blocking production pending human and ISO/QEMU gates. Runtime, builds, installs and tests were **not run**; this is a partial static review, not certification.

The pinned historical Actions run failed before tests. Source shows silent deletion errors, plaintext backup staging and response handling defects. Independent image, networking, recovery and human reviews block release; Go CI cannot substitute. See [remediation plan](REMEDIATION_PLAN.md).

## Architecture and product boundary

The [client entry point:18–42](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/cmd/deaddrop-client/main.go#L18-L42) selects TUI, CLI or self-test; the [TUI:43–101](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/client/tui/app.go#L43-L101) encrypts, submits, retrieves and decrypts. ## Findings ledger

**D01 — High, confirmed static, high confidence: backup plaintext on disk.** [backup-deaddrop.sh:8–13](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/deploy/scripts/backup-deaddrop.sh#L8-L13) writes a database backup and onion-key archive before `gpg --encrypt`, then runs `shred -u` only after both encryptions. With `set -e`, an earlier failure can leave plaintext, including onion identity material; neither restrictive permissions nor secure erasure on all storage can be assumed. Use private temporary storage, cleanup traps, encrypted streaming where feasible, and failure-path tests; review backup access and retention.

**D02 — Medium, confirmed static, high confidence: delete acknowledges storage failure.** [server/server.go:172–184](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/server/server.go#L172-L184) discards `_ = s.store.DeleteDrop(...)` and returns `StatusNoContent`; [storage.go:99–104](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/server/storage.go#L99-L104) can return a database error. A failed delete appears successful, leaving a drop present. Preserve the intended indistinguishable successful/nonexistent response while reporting actual storage errors without leaking IDs.

**D03 — Medium, confirmed static, high confidence: malformed success can appear submitted.** [client/tui/main.go:28–43](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/client/tui/main.go#L28-L43) ignores both `io.ReadAll` and `json.Unmarshal` errors and returns `out.ID`; [app.go:56–61](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/client/tui/app.go#L56-L61) displays submitted status on nil error. A malformed 201 or failed read can produce a false success with an empty ID. Bound the response, propagate errors and validate the returned ID.

**D04 — High, historical CI, high confidence about observed result only.** [Run 27439860776](https://github.com/knarayanareddy/DEADDROP-OS/actions/runs/27439860776) at the pinned SHA failed on `./tools/check-go-version.sh`; test, vet, build, invariant scan, vulnerability scan and artifact upload were skipped. The [workflow:8–17](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/.github/workflows/ci.yml#L8-L17) requests Go `1.25.11`. The failure cause is not established from job status; inspect the logs and reproduce before changing the version policy. No test result or present-day branch status is inferred.

**D05 — High, unverified risk, medium confidence: network and memory guarantees depend on deployment.** [firewall.sh:9–29](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/client/firewall/firewall.sh#L9-L29) flushes rules before setting DROP policies and adds Tor redirects; whether startup, failure or restart permits a leak depends on actual system/network state. [client main:19–25](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/cmd/deaddrop-client/main.go#L19-L25) allows a configurable key directory and treats memory locking as best effort. No claim that non-tmpfs paths are rejected is supported. Test failure and reboot paths on an isolated lab image and make unsafe configurations explicit or fail closed as approved.

**D06 — High, unverified risk, high confidence about gate limitation.** [QEMU harness:12–32](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/tests/qemu/run-qemu-security-tests.sh#L12-L32) passively rejects IPv6 and non-DHCP UDP, then announces `QEMU passive capture checks passed`. It does not by that result establish TCP Tor-only routing, correct guest boot, successful active lifecycle, or wipe/amnesia. Require positive capture/guest evidence and active negative controls; an empty or unreadable capture must not count as security proof.

## Five-discipline assessment

- **Correctness/code:** D02 and D03 are source-confirmed error-path defects, not reproduced failures. The [existing server test:39–62](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/server/server_test.go#L39-L62) exercises a handler submit/retrieve happy path using an in-memory database; it cannot establish OS behavior or error handling.
- **Automation/testing:** D04 establishes a historical skipped test suite, not a current pass. CI includes Go tests, vet, static checks and binary artifacts, but the inspected workflow contains no ISO or QEMU step. D06 needs active and negative controls. The [readiness checklist:25–35](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/release/PRODUCTION_READINESS.md#L25-L35) requires two independent ISO builds; no build was observed.
- **DevOps/operations:** [deployment docs:3–8](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/docs/SERVER_DEPLOYMENT.md#L3-L8) specify Debian 12, Tor and persistent SQLite/onion key. D01 makes backup failure handling a priority; a script or runbook alone is not a restore. Service permissions, monitoring, release signing, rollback and recovery remain unverified.
- **OWASP/security:** The [security model:14–22](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/docs/SECURITY_MODEL.md#L14-L22) declares no accounts. [get and delete handlers:147–184](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/server/server.go#L147-L184) expose hint-based retrieval and ID-based deletion without identity authorization in those handlers; whether bearer-like identifiers meet the threat model is an owner decision, not proof of a vulnerability. [storage.go:75–81](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/server/storage.go#L75-L81) uses SQL parameters, reducing injection risk in these queries only. [go.mod:3–8](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/go.mod#L3-L8) declares dependencies, while CI installs `govulncheck@latest` and uses mutable action tags; dependency integrity and advisories remain unverified. No secret scan, cryptographic audit, or transport validation was performed.
- **UI/UX/accessibility:** This is a terminal interface, not a browser UI. D03 affects user trust; [app.go:29–33](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/client/tui/app.go#L29-L33) exposes compose, retrieve, public key and quit. Keyboard-only operation, screen-reader compatibility, terminal sizes, error clarity and activity/panic interactions require user testing; accessibility is not established by source.

## Production blockers and owner decisions

Name a security lead and reporting channel; choose acceptable hint/ID possession semantics and ADR-05 TLS-on-onion policy. Provide a segregated lab, test onion service, packet-capture capability and representative boot hardware. Assign backup encryption recipients and recovery custodians, release signer, signing-key custody, independent builders and incident contacts. The [readiness checklist:37–50](https://github.com/knarayanareddy/DEADDROP-OS/blob/38b8e706304ea551d59b77fd6bc9f2ef7ed89bb9/release/PRODUCTION_READINESS.md#L37-L50) lists human, restore, onion-key, image and QEMU gates; their completion is not evidenced here.
